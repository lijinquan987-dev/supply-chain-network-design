## 1. 项目缘起：一个业务问题的数学化

### 1.1 业务痛点（为什么做）

分仓决策（「几个仓、放哪里、覆盖谁」）是供应链网络设计（Supply Chain Network Design）的核心问题。常见困境：

- **拍脑袋定仓**：凭经验和行政区域划分仓网，缺乏量化依据；
- **只算运费**：只盯配送成本，忽略仓储与补货成本的联动；
- **只看单点**：看单一仓的成本或时效，不评估全网（Network）整体表现；
- **不可复算**：方案无法被验证、复制到其他品类/区域/场景。

### 1.2 研究问题（要回答什么）

基于既往分仓实践经验，用 P-中值选址模型（P-Median Model）量化回答：

1. **仓数**：不同仓数 P 下，总成本（仓储 + 补货 + 配送）如何变化？
2. **选址**：给定仓数，最优仓址在哪里？哪些城市应被哪个仓覆盖？
3. **权衡**：增加一个仓的**边际成本** vs **时效收益**，是否划算？
4. **达标**：次日达（D+1）达成率能达到什么水平？时专城市是否满足？

### 1.3 项目目标（交付什么）

- 一套**可复算**的选址模型（Excel + OpenSolver 与 Python + CBC 双轨实现，交叉验证）；
- 一组**决策依据**：仓数-成本-时效权衡曲线、9 仓甜点区结论、覆盖分配方案；
- 一套**可迁移**的方法论：任何行业、任何规模的分仓/分拨/分仓选址问题均可复用。

## 2. 数据准备与口径（Data & Assumptions）

> 原则：**公开数据做骨架，经验参数做假设，所有口径可审计、可复算。**

### 2.1 数据获取（真实 API 流程）

| 数据 | 获取方式 | 规模 | 用途 |
|---|---|---|---|
| 行政区经纬度 | 高德开放平台 **地理编码 API** + Python 批量查询 | 337 个需求点 = 333 地级行政区 + 4 直辖市（京/沪/津/渝） | 需求点坐标 |
| 城间运距 | 高德开放平台 **距离测量 API** + Python 批量查询 | 337 × 15 = 5055 条（需求点 → 候选仓）+ 15 条（总仓 → 候选仓） | 配送/补货运距 |
| 城市 GDP | 公开统计口径 | 337 城市 | 需求量拟合 |

> 安全红线：高德 API Key 只存本地环境变量，绝不进入代码仓库（`.gitignore` 已排除 `.env`）。

### 2.2 需求假设：按 GDP 占比拟合业务量

需求量（业务量）无真实数据，采用**城市 GDP 占比拟合**：

```
城市 i 的日均单量 = 总日均单量 × 城市 i 的 GDP / Σ 全部城市 GDP
```

- 总量假设：**60,164 单/日**；
- 单量 Top10 与城市 GDP 排名高度一致（上海 2,425 > 北京 2,241 > 深圳 1,655 > 重庆 1,448 > 广州 1,396 > 苏州 1,202 > 成都 1,058 > 杭州 983 > 武汉 949 > 南京 832），拟合逻辑成立；
- 单均重量统一按 **0.35 kg/单**。

### 2.3 时效梯度：按运距分档（从业经验假设）

基于快递履约经验，将**运距 → 时效**划分为四档（本项目的核心业务假设）：

| 运距区间 | 时效等级 | 时效 SLA | 说明 |
|---|---|---|---|
| ≤ 450 km | D+1 | ≤ 24 h | 省内及邻近区域，次日达 |
| 450 ~ 1,300 km | D+2 | ≤ 48 h | 区域配送 |
| 1,300 ~ 2,200 km | D+3 | ≤ 72 h | 跨区域配送 |
| > 2,200 km | D+4 | ≤ 96 h | 远距离干线 |

> 数据佐证（`distance_cost.csv` 5055 条）：SLA=24h 的组合运距 0~448km、48h 为 452~1299km、72h 为 1301~2199km、96h 为 2202~5412km，分档边界与假设完全吻合。

### 2.4 时专（专属时效）：核心城市强约束

- **时专矩阵**（`8_时专` sheet）：6 个核心城市（**上海、北京、深圳、重庆、广州、苏州**，即 GDP/单量 Top6）无论分配给哪个候选仓，时效目标均为 **D+1（4 级）**；
- 这是项目的**分级时效硬性要求**，用于评估候选方案的「指定城市必须达标」能力。

### 2.5 目标时效矩阵（分级目标）

- `9_时限` sheet：337 需求点 × 15 候选仓 = 5055 格的目标时效矩阵；
- 分布：D+1（4 级）33% / D+2（3 级）47% / D+3（2 级）4% / D+4（1 级）16%；
- 每格含义：该需求点若分配给该仓，业务目标要求达到的时效等级。

### 2.6 仓容（产能上限）

- `10_容限` sheet：全部候选仓容量阈值统一为 **60,164 单/日**（= 总单量）；
- 含义：任何单仓都不应承载超过全网总量的产能——现实中为**弱约束**（当前方案无仓超限，不构成硬性阻断），但模型已具备容量约束能力（见[变种 7.1](#71-容量约束变种)）。

### 2.7 成本假设（三成本口径，与 Excel 模型一致）

| 成本 | 口径公式 | 参数 |
|---|---|---|
| 仓储 | 单量 ×（单均固有分摊 + 单均操作费） | 固有分摊 0.25 / 0.28 / 0.30 元/单（按仓分档）+ 操作费 1.8 元/单 |
| 补货 | 单量 × 0.35 kg/单 × 补货运距单价（元/kg） | 按运距六档：0.8 / 1.2 / 1.5 / 1.7 / 1.9 / 2.2 元/kg |
| 配送 | 单量 × 单均快递成本（元/单） | 按运距五档：0-300km→6~7 元、300-600→7~9、600-1000→9、1000-2000→12~15、>2000→19~22 |

> 简化说明：单均配送成本按「运距分档单均价」假设，严格口径应按订单类型 × 公斤段 × 配送计费规则计算，本模型为方法演示而简化，不影响方法论成立。

## 3. P-中值模型：从业务语言到数学语言（逻辑层）

### 3.1 为什么是 P-中值模型（P-Median Model）

设施选址（Facility Location）三大经典模型：

| 模型 | 目标 | 适用场景 | 本项目的选择 |
|---|---|---|---|
| **覆盖模型**（Covering） | 使「被覆盖的需求」最大化 | 应急设施、限时可达 | ✗ 成本维度弱 |
| **重心法**（Center of Gravity） | 使最大距离最小化 | 单设施、近似求解 | ✗ 无法处理多仓与约束 |
| **P-中值模型** | 使「加权运输成本」最小化 | **多仓选址、成本驱动** | ✓ **本项目采用** |

P-中值模型把「物流成本最小化」作为第一目标，天然契合「降本」这一业务诉求，同时可叠加容量、时效、分级目标等约束。

### 3.2 数学模型（Mathematical Formulation）

```
集合（Sets）
  I = {1, ..., 337}    需求点（地级行政区）
  J = {1, ..., 15}     候选仓

参数（Parameters）
  wᵢ          需求点 i 的日均单量（单/日）
  cᵢⱼ         需求点 i 分配给候选仓 j 的每日全成本（仓储 + 补货 + 配送）

决策变量（Decision Variables）
  xᵢⱼ ∈ {0,1}   需求点 i 是否分配给候选仓 j
  yⱼ  ∈ {0,1}   候选仓 j 是否开设

目标函数（Objective）：最小化全网每日总成本
  minimize  Σᵢ Σⱼ cᵢⱼ · xᵢⱼ

约束（Constraints）
  Σⱼ xᵢⱼ = 1                     ∀ i      # 每个需求点被且仅被一个仓覆盖
  xᵢⱼ ≤ yⱼ                        ∀ i, j   # 需求点只能分配给已开设的仓
  Σⱼ yⱼ = P                                # 恰好开设 P 个仓
  Σᵢ wᵢ · xᵢⱼ ≤ Capⱼ             ∀ j      # 容量约束（可选，本项目弱约束）
  xᵢⱼ, yⱼ ∈ {0, 1}                        # 0-1 决策变量
```

### 3.3 业务语言 → 数学语言的映射

| 业务问题 | 数学表达 |
|---|---|
| 每个城市只能由一个仓发货 | `Σⱼ xᵢⱼ = 1` |
| 没开的仓不能发货 | `xᵢⱼ ≤ yⱼ` |
| 老板说就开 9 个仓 | `Σⱼ yⱼ = 9` |
| 这个仓产能只有 X 单 | `Σᵢ wᵢ · xᵢⱼ ≤ X` |
| 哪个仓发货总成本最低 | `min Σᵢ Σⱼ cᵢⱼ · xᵢⱼ` |
| 指定城市必须次日达 | 时效为软/硬约束（见变种 7.2） |

### 3.4 成本矩阵的构建（业务口径 → 模型参数）

每个「需求点 i → 候选仓 j」组合的成本 `cᵢⱼ` 由三部分构成（与 Excel 0_总表逐行一致）：

```
cᵢⱼ = 仓储ᵢⱼ + 补货ⱼ + 配送ᵢⱼ
     = wᵢ × (固有分摊ⱼ + 操作费)         # 仓储：取决于候选仓 j 的成本档
     + wᵢ × 0.35 × 补货运距单价ⱼ         # 补货：取决于总仓→候选仓 j 的干线
     + wᵢ × 单均快递成本ᵢⱼ               # 配送：取决于需求点 i 与候选仓 j 的运距
```

## 4. 双轨求解：工具与过程（工具层）

采用**双轨实现 + 交叉验证**，兼顾业务可用性与工程可复现性。

### 4.1 轨线 A：Excel + OpenSolver（业务侧）

**角色**：业务团队可视化建模、逐行审计、快速调整参数。

| 环节 | 实现 |
|---|---|
| 基础数据 | `0_总表`（5055 行：需求×候选组合，含运距/成本/时效/指派） |
| 决策变量 | `模型` sheet：U 列 342 个「候选仓指派 ID」0-1 变量（337 需求 + 5 辅助） |
| 目标函数 | `模型` sheet：仓储 + 补货 + 配送三成本求和（579,165 元/日） |
| 约束 | 单覆盖（SUM=1）、仓数（选中状态合计=P）、选中仓与指派联动（COUNTIF） |
| 求解器 | **OpenSolver**（Excel 开源求解器，CBC 内核，支持整数规划） |
| 时效看板 | `模型` sheet 右侧：目标限定城市、分层单量、区间达成率（D+1 命中 42888 单） |

**产出**：9 仓方案（HC02/HC03/HC04/HC05/HC06/HC09/HC10/HC11/HC15，即广州/成都/无锡/长沙/郑州/厦门/潍坊/长春/保定）。

### 4.2 轨线 B：Python + CBC（工程侧）

**角色**：批量扫描、边际分析、可复现、可扩展。

| 环节 | 实现（本仓 `src/`） |
|---|---|
| 数据读取 | `model_full.py`：读取 `data/processed/*.csv`，按 3.4 口径构建成本矩阵 |
| 模型构建 | `pulp`（Python 线性规划库）声明式建模 |
| 求解器 | **CBC**（COIN-OR 开源混合整数规划求解器） |
| 边际扫描 | `sweep_p.py`：P=1..15 逐一求解，输出成本/时效/边际 |
| 可视化 | `plot_results.py`：9 仓覆盖图 + 成本时效比选图 |

### 4.3 交叉验证协议（Cross-Validation Protocol）

```
输入（同一套数据）──┬──▶ Excel + OpenSolver ──▶ 方案 A（9 仓）
                    └──▶ Python + CBC ──────▶ 方案 B（9 仓）
                                              │
                              对比：仓集是否一致？成本是否吻合？
```

**验证结果**：

| 指标 | Excel + OpenSolver | Python + CBC | 一致性 |
|---|---|---|---|
| 9 仓仓集 | 广州/成都/无锡/长沙/郑州/厦门/潍坊/长春/保定 | 同左（9 个仓 ID 完全一致） | ✓ 100% |
| 每日总成本 | 579,165 元/日 | 579,082 元/日 | **误差 0.014%** |
| 成本构成 | 仓储 124,882 + 补货 31,166 + 配送 423,118 | 仓储 124,915 + 补货 31,049 + 配送 423,118 | 结构一致 |

双轨独立实现、同一口径、结果高度一致——**模型可信**。

### 4.4 关键工程经验（Engineering Notes）

1. **求解器版本兼容**：`pulp 4.x` 移除了 `LpVariable.dicts` / `fromDicts` API，本仓锁定 `pulp==2.7.0`（见 `requirements.txt`）；
2. **变量命名清洗**：pulp 会将元组变量名清洗成 `('上海',_'深圳')` 形式，从解中提取变量应按**变量字典引用**而非解析名称；
3. **软约束 vs 硬约束**：Excel 时效为「达成率/偏移」软约束（允许部分未达标并统计偏移），若改为硬性过滤（`--time-filter`）会 Infeasible——业务上应选软约束 + 达成率看板；
4. **容量阈值**：60,164 = 总单量，实际不构成硬约束，但保留在模型中以支持容量场景。

## 5. 结果与决策闭环

### 5.1 核心结论

**9 仓是成本—时效权衡的甜点区（Sweet Spot）**：

| 仓数 P | 总成本（元/日） | D+1 达成率 | 边际成本（元/日） |
|---|---|---|---|
| 2 | 701,762 | 21.2% | — |
| 5 | 612,017 | 61.4% | -13,582 |
| **9** | **579,082** | **81.2%** | **-5,493** |
| 12 | 569,724 | 86.6% | -2,269 |
| 15 | 567,155 | 88.0% | -396 |

- **边际收益递减**：P 从 1→5 每加一仓平均省 4.6 万元/日（时效快速改善）；P 从 9→15 每加一仓只省约 0.2 万元/日；
- **9 仓 vs 2 仓业务初始方案（北京+广州）**：总成本降低 **38.9%**（948,329 → 579,165 元/日），D+1 达成率从 7.3% 提升至 **82.8%**；
  > 口径注：表中 P=2 的 701,762 元/日/21.2% 是**数学最优 2 仓组合**（扫描求解），948,329 元/日是**业务直觉方案**（北京+广州）——「直觉 vs 算法」的对比用后者。
- 完整数据见 `results/sweep_p1_15.csv`。

### 5.2 闭环验证（项目目标达成情况）

| 研究问题 | 答案 |
|---|---|
| 几个仓？ | 9 个（甜点区，边际收益衰减起点） |
| 放哪里？ | 广州/成都/无锡/长沙/郑州/厦门/潍坊/长春/保定（算法最优解） |
| 覆盖谁？ | 337 城市按成本最优分配（见 `assignment_9hubs.csv`） |
| 成本多少？ | 579,165 元/日（双轨验证误差 0.014%） |
| 时效如何？ | D+1 达成率 82.8%（2 仓方案仅 7.3%） |
| 时专达标？ | 6 个核心城市（沪京深渝广苏）无论分仓均满足 D+1 |

**闭环**：业务问题 → 数据与假设 → 数学模型 → 双轨求解 → 交叉验证 → 决策结论。

## 7. 变种与复合场景（Framework Variants）

### 7.1 容量约束变种（Capacity-Constrained）

- 当候选仓有真实产能上限（如仓库面积、吞吐能力）时，将弱约束升级为硬约束：
  `Σᵢ wᵢ · xᵢⱼ ≤ Capⱼ`
- 本项目 10_容限 = 60,164（总单量）为弱约束；真实场景应使用各仓实际产能。

### 7.2 时效硬约束变种（Service-Level Constrained）

- 将「达成率软约束」升级为硬约束：指定城市集（时专）的 SLA 必须 ≤ 目标半径；
- 经验：硬约束容易 Infeasible（本项目验证），业务上推荐「软约束 + 达成率看板 + 超限惩罚项」三件套。

### 7.3 多层级仓网（Multi-Echelon）

- 扩展为「总仓（RDC）→ 区域仓（FDC）→ 前置仓（DC）」多层级：
  - 第一层：总仓 → 区域仓（补货干线）
  - 第二层：区域仓 → 需求点（配送末端）
- 决策变量增加层级指派，目标函数叠加各层成本。

### 7.4 多周期动态选址（Multi-Period）

- 需求随时间变化（季节性、增长趋势）时，扩展为多周期模型：
  - 每个周期独立选址 → 增加「开仓/关仓」转移成本
  - 约束增加连续性（相邻周期仓集变化限制）

### 7.5 多品类多模式（Multi-Product / Multi-Mode）

- 多品类：不同品类时效目标/成本分档不同 → 按品类拆分需求矩阵；
- 多模式：快递/快运/整车混用 → 每个「需求-仓-模式」组合独立成本。

### 7.6 复合场景组合（Composite）

| 场景 | 组合的变种 |
|---|---|
| 电商大促备货 | 容量约束 + 多周期（促销高峰前置仓） |
| 冷链网络 | 时效硬约束 + 多层级（冷库分级） |
| 医药合规仓网 | 时专硬约束 + 容量约束 + 品类拆分 |
| 出海多国仓网 | 多层级 + 多周期（建仓节奏） |

## 8. 已知局限与改进方向

| 局限 | 说明 | 改进方向 |
|---|---|---|
| 需求量假设 | GDP 拟合为近似，非真实订单 | 接入真实订单数据/预测模型 |
| 时效梯度假设 | 按运距四档简化 | 用实际履约 SLA 数据校准 |
| 配送成本简化 | 按单均分档，未拆订单类型/公斤段 | 引入计费规则模型 |
| 静态单周期 | 未考虑需求动态 | 多周期动态选址（7.4） |
| 距离用 API 行政中心 | 未做路网级精确测算 | 接入路径优化引擎 |
| 单一目标 | 只优化成本 | 多目标（成本 + 时效 + 碳排放）帕累托分析 |
